# 背景と失敗例（2026-10-08 の検証から）

検証に使ったもの: iPhone で手持ち撮影した 26 s の動画（1280×720、30 fps、書き出し済み）と、
同じ晩の走行 20 本（data_20261007_*、地図 map_20260906_174134、自己位置 fused）。
結論: data_20261007_214644 の 21:48:34.34 から。2 位との差 0.13、±0.1 s で誤差が 3 倍、通過時刻は ±0.2 s で一致、位置 p50 0.18 m。

## 1. メタデータの時刻

- mp4 の `creation_time` とファイル名（`813081385.015508` = Apple の基準時刻 2001-01-01 からの秒）はどちらも 10/08 00:56:25。
  走行はすべて 21:49 までに終わっていた → **書き出し（共有・トリミング）した時刻**。撮影時刻ではない。
- 使い道は「走行の候補を絞る」だけ。合わなければ捨てて全走行を探す（探索は 20 走行で十数秒）。

## 2. やってはいけない: 車の軌跡だけで画像⇔地図のホモグラフィを当てはめる

- 走行ごと・時刻差ごとに「画像上の車の位置 ⇔ 自己位置」で RANSAC ホモグラフィを当てはめると、一致率 0.97 で「当たった」ように見えた。
  しかし推定した変換でコース外形を描き戻すと柵とまったく合わない。2 位の別の走行も 0.95。
- 原因: 見える範囲の車の軌跡はほぼ一直線の曲線で、自由度 8 のホモグラフィは平面を潰した解でいくらでも当てはまる。
  カメラモデル（PnP）にしても同じ点群からは不安定（カメラ位置が無限遠に飛ぶ）。
- **教訓**: 較正は動かない構造（柵・コースの外形）で決め、時刻差の探索はカメラを固定した 1 次元で行う。

## 3. 柵 × 外形の自動較正

- 柵のマスク: HSV の赤（H 0–10, 165–180、S>90、V>70）と白（S<40、V>170）。天井・カーテン（上 40%）と手前の机を除く。
- 地図の外形（map_bounds.json の outer と holes、高さ 0.05 m の帯）を投影し、
  コスト = 外形→柵の距離（平均、30 px で頭打ち）＋ 柵→外形の距離 ＋ 30×(1−広がりの IoU)。
  - 片方向（外形→柵）だけだと、外形を数本の柵に重ねて潰した解に逃げる。
  - 広がりの IoU（外接矩形の重なり）を入れないと、遠くから小さく写す解に逃げる。
- 変数: カメラ位置 (x, y, z)、注視点 (x, y)、ロール、焦点距離 f、歪み k1。ランダム 6000 点 → 上位 12 点から Nelder-Mead。
- **カメラの側のヒントが要る**: 範囲を絞らないと、コスト 22.5 の誤った解（外形が柵に沿わない）に落ちた。
  正しい側を `--cam-box` で与えるとコスト 17.7 で正解（外形が U 字の仕切りまで重なる）。コスト自体は正解を低く評価しているので、
  迷ったら側ごとに回して最小を採ればよい。
- 結果の例: カメラ (7.20, −2.59, 高さ 1.67) m、f ≈ 600 px（iPhone の広角寄り）。

## 4. 車の検出

- 手ぶれ補正: ORB 3000 点 → 基準フレーム（中央）へ RANSAC ホモグラフィ。手持ち 26 s で全フレーム成功（対応点の最少 362）。
- 背景 = 補正後のフレームの中央値。差分 > 40、面積 25–4000 px（640 幅）、前フレームの位置に近い塊を優先。
- **検出はコースの範囲（外形を投影した領域）に限る**。限らないと、手前の机やモニター付近の動きを車と取り違えた（4–16 s）。
- 車は 10–15 px と小さく、奥のレーンは仕切りに隠れて抜ける。見えるのは主に手前のレーン。

## 5. 時刻差の探索

- 車は 1 周 8 秒前後で同じ所を通るので、**位置が合うだけでは周回の位相が似た別の走行と区別しにくい**。
  そこで両方向で数える: 検出があるのに投影が遠い（外れ）、投影が「検出が出る領域」にいるのに検出が無い（見逃し）。
  F = 2×一致 / (検出数 + 見えるはずの数)。
- 粗く 1/15 s、上位を 1/120 s で詰める。`offset_curve` の鋭さ（±0.1 s で誤差が何倍になるか）が信頼度の目安。
- 車の点は後軸から前へ 0.13 m、高さ 0.06 m（検出する塊の中心に近い）。
- フレーム時刻は OpenCV の `CAP_PROP_POS_MSEC`（最終フレームで 0 に戻ることがあるので補間）。フレーム番号/fps で数えると可変フレームレートでずれる。

## 6. 精度の限界

- 位置の一致 p50 0.18 m（手持ち・広角・遠景）。原因: 車が小さい、塊の中心と車体の中心のずれ、歪み（k1 のみ）、手ぶれ補正の残差。
- cm 単位の真値には、三脚・近距離・チェッカーボードでの歪み較正・ルーフのマーカー（または YOLO のキーポイント）が要る。

## 7. iPhone のオリジナル（IMG_3320.MOV）での再検証

- 形式: HEVC Main10、HDR（HLG・Dolby Vision profile 8）、1920×1080、29.99 fps、iPhone 12 mini。
  `com.apple.quicktime.creationdate: 2026-10-07T21:48:34+0900`（moov は末尾。mvhd の作成時刻も同じ UTC 12:48:34）。
- **映像だけで求めた t=0（21:48:34.337）とメタデータの撮影開始（21:48:34）が秒で一致** → 手順の正しさの独立な裏付け。
  書き出し版 mp4 と MOV で求めた時刻差はミリ秒単位で一致（.337 / .337 / .341）。
- OpenCV（Jetson の 4.5.4、FFmpeg バックエンド）で HEVC 10 bit をそのまま読めた（tone map なしなので白っぽい）。
  柵のマスクは `--hdr`（ガンマ 1.6 ＋ 彩度 ×1.6）で、カーテンの裾の誤検出が減り赤が戻った。
- 較正: HDR 補正後でもゼロからは IoU 0.885（コスト 24.4）止まり。書き出し版の較正を `--init` にすると IoU 0.98（20.3）で全柵に一致。
  焦点距離 894 px（書き出し版 602.9 × 1.5 = 904 とほぼ同じ）、カメラ位置もほぼ同じ。
- 結果: 2 位との差 0.08（書き出し版 0.13 より小さいが 1 位は同じ）、主な 3 通過の開始時刻の差 0.00 / 0.04 / 0.03 s、
  位置 p50 0.20 m・p90 0.47 m（書き出し版 p90 5.6 m → 1080p で誤検出が大きく減った）。
